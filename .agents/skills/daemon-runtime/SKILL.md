**Daemon Singleton Lock (`internal/daemon/lock.go`)**

- Only one live daemon may own an `NM_HOME`: an exclusive OS file lock on `<NM_HOME>/daemon.lock` is acquired as the very first action in `RunWithOptions`, strictly before stale-run recovery and socket bind, and held for the process lifetime. The kernel releases it on any process death, so a held lock always means a live holder and no staleness heuristic is needed. Without it, a second daemon stole the socket and ran global crash recovery against the live daemon's runs and worktrees.
- Process launch is not readiness: the PID record is published after the singleton lock and before exclusive recovery, while startup succeeds only after a real IPC health response. The 45s production budget covers cold environment setup and recovery; early exits fail promptly, timeout cleanup reaps detached children before fallback or rollback, and managed plus detached failures retain both causes. Regressions: `TestStartDetachedDaemonDetectsChildExitPromptly`, `TestStartDetachedDaemonTimeoutKillsAndReapsChild`, `TestStartPreservesManagedAndDetachedFallbackErrors`, `TestColdDetachedStartupProductionGateCardinality`.
- A successful stop means the daemon process is gone, not merely that IPC health has disappeared, because only process exit releases the singleton lock. Capture the daemon instance before requesting shutdown, and close the shutdown client before waiting because the daemon drains in-flight handlers during exit. See `waitForDaemonStop` and `stopDetachedDaemon`; regressions: e2e `TestDaemonStopLeavesNoDaemonProcessOwningTheRoot`, `TestDaemonRestartReplacesTheDaemonWithExactlyOneOwner`.
- Independent layers: `internal/ipc` `listen()` dials the socket before unlinking it and refuses to steal a live one; client probes bound the dial with `daemon_connect_timeout` and fail fast on a dead or wedged socket instead of starting a replacement daemon (`EnsureDaemon` surfaces the error with a `daemon start` recovery hint; the health RPC itself is bounded separately by `ipc.DefaultDialTimeout`).
- Daemon execution is explicit-only (`no-mistakes daemon run --root`); never let inherited environment reinterpret probes like `--version` or `status` as daemon workers.
- Startup worktree cleanup is DB-aware: never remove a worktree whose run row is `pending` or `running`; `startRun` inserts the run row before creating the worktree, so a no-row directory is safe to remove immediately. That no-row rule holds only inside `<NM_HOME>/worktrees`, which is discovered by walking because no-mistakes owns it; a configured worktree root is the operator's directory, so cleanup and eject there act on exactly the recorded run worktrees and never enumerate anything else.
- The user-facing model lives in `docs/src/content/docs/concepts/daemon.md`; the lock rationale lives in the `internal/daemon/lock.go` and `daemon.go` comments. Regressions: `TestAcquireSingletonLock_*`, `TestRunWithResources_SecondDaemonForSameRootFailsWithoutStealingSocket`, `TestRunWithOptions_RequiresSingletonLockBeforeRecovery`, `TestRecoverOnStartup_DoesNotDeleteActiveRunWorktree`, `TestServe_SecondListenerForLiveSocketDoesNotStealIt`, `TestDialConnectTimeoutFailsFastAndNamesSocket`, `TestIsRunningFailsFastWhenSocketAcceptsButDoesNotRespond`, `TestIsRunningSurfacesExistingDeadSocket`, `TestDaemonRunRootFromArgs_EnvDoesNotForceDaemonModeForProbes`, `TestValidateDaemonPIDFallback_RefusesToKillOwnProcess`.

**IPC Protocol Version Handshake**

- `ipc.ProtocolVersion` (`internal/ipc/protocol.go`) versions the daemon wire contract; bump it whenever a change makes an older peer's understanding of the protocol wrong. `NewRequest` stamps it on every request, and `HealthResult` reports the daemon's.
- Three meta methods stay reachable for a skewed peer (`versionExemptMethod`): `health` is the negotiation method, `shutdown` is how any peer ends the daemon, and `gate_context` is the recursive-containment query that every pipeline-control command runs first, so gating it would deadlock `daemon stop`, `daemon restart`, and `update` behind the very error naming them. Their param and result wire shapes are therefore pinned as version-independent: any change to them must stay backward and forward compatible, because a peer on any version may call them. `Server.handleConn` gates every other method on an exact match before the stream lookup and dispatch, so a skewed peer's handler never runs and no stream starts; one integer compare on a field already present keeps read-only calls at zero extra round trips.
- The git hooks (`daemon admit-push`, `daemon notify-push`) are the one caller with no health probe ahead of them, so `AdmitPushResult`/`PushReceivedResult` carry the daemon's `protocol_version` and the hook checks it with `ipc.DaemonVersionMismatch` before trusting the payload: no extra round trip, and a drifted reply can never decode as a permissive not-nested verdict. The pre-receive `admit-push` check is the enforcing gate that rejects the ref update; the post-receive `notify-push` check is a post-hoc report, because the ref has already moved by then. A daemon predating `gate_context` answers method-not-found, which `classifyGateControlCaller` treats as grounds to fall back to the local `gatecontext.Inspector` only when the peer also reports NO version (`Remote == 0`); a peer that declares a version and still lacks the method is a future protocol, and degrading containment for it would be a bypass. That single bounded exception is a deliberate weakening, not a preserved invariant: for a version-0 daemon that predates the method, containment degrades to local cwd/marker/DB classification with no authenticated peer ancestry, which is weaker than base for that one population and is the accepted price of keeping the remedy reachable. Every other skew still queries the authenticated peer over the exempt method or fails closed. `init` reports a skew, keeps the gate it just created, and says so on stderr, because a skew is a refusal to proceed, not a failed setup.
- The mismatch message names the remedy for whichever side is STALE (on the lower version), not for whichever side detected the skew, which is only accidentally correct while stale means version 0. `Error()` renders summary plus remedy; `Summary()` and `Remedy()` split them for a fixed-width status row such as `doctor`'s.
- A mismatch fails closed and never starts a replacement daemon: `daemonIsRunningViaIPC` reports not-alive plus an `ipc.VersionMismatchError` (an old daemon omits the field, so it reads as version 0), `EnsureDaemon` returns that error unwrapped instead of calling `daemonStart`, and `Start` returns it before any launch. Classify with `ipc.IsVersionMismatch`, which matches both the local error and a peer-reported `ErrProtocolMismatch`.
- A mismatched daemon is alive, so `daemonHealthCheck`/`daemon.IsRunning`'s `alive` bool alone is not enough for a decision that would kill it, replace it, weaken a containment guard, or report an already-reached end state: read the error too, via the explicit `alive, err := daemonHealthCheck(...)` plus `ipc.IsVersionMismatch(err)` idiom. Guarded so far: `Start`'s top guard, `Start`'s shared re-check immediately before the detached fallback (covering the install-failure and managed-timeout branches alike), `waitForDaemonStartWithProcess`'s early return so a settled skew never burns the readiness budget (which then splits on identity: a skew from the child this call launched IS readiness, because self-update replaces the executable before resetting the daemon, so an old CLI supervising a newer child is the normal upgrade path and reaping it would destroy the daemon the update installed; `launchedChildAnsweredSkew` identifies that child by pid for a detached launch and by a PID record no older than the launch for a managed one, and every other answering daemon is reaped and reported), `startManagedDaemon`'s launch-failure branch, where a skewed daemon means the end state it would report as already reached is not reached, `Start`'s managed branch, which returns a skew immediately rather than booting a healthy foreign daemon through `stopManagedFallback` on the way to reporting it, `reconcileCollidingDaemons`'s per-candidate check before `daemonKillPID`, `classifyGateControlCaller` (which asks the skewed daemon over the exempt `gate_context` rather than degrading recursive-gate containment to the `PeerPID == 0` cwd-only path), `daemonAliveForConfigDeferral` (a live daemon defers a broken global config; a skewed one is still live), `runAxiAbortByRunID`, and `ensureDaemonUsesCurrentExecutable` (a mismatch is the strongest evidence of a different-executable daemon, so it must reach the takeover prompt). Each site's response differs, which is why there is no shared boolean helper. Also guarded: `daemonPIDRecordMatchesProcess`, so a legacy start-time-less PID record still validates against a skewed daemon and `daemon stop` can prove the process it waits for exited. The residual sites that still read the bool alone are `waitForDaemonStop`, `Stop`, `stopCurrentDaemonBeforeManagedRestart`, and `stopManagedFallback`, all in the `internal/daemon` shutdown path a sibling worker owns, and each degrades rather than fails: `waitForDaemonStop` requires `err == nil`, so while a skewed daemon is still answering it burns the whole stop budget before falling back to the PID kill; the other three read a skewed daemon as absent, so `Stop` and `stopCurrentDaemonBeforeManagedRestart` skip their detached shutdown request and `stopManagedFallback` never reports "managed daemon is still running". Add the idiom there when that path is next touched. Read-only surfaces (`axi` home, `status`) still render a skewed daemon as stopped; that is an accepted tradeoff, not an oversight. Regressions: `internal/ipc/protocol_version_test.go`, `internal/ipc/version_test.go`, `internal/daemon/protocol_version_test.go` (incl. `TestStart_VersionMismatchReturnsErrorWithoutLaunching`, `TestStart_InstallFailureBranchReturnsVersionMismatchWithoutDetachedFallback`, `TestReconcileCollidingDaemons_VersionMismatchedStrayIsNeverKilled`, `TestStartDetachedDaemon_SkewFromTheChildThisCallLaunchedIsReadiness`, `TestWaitForManagedDaemonStart_SkewFromAForeignDaemonStaysAMismatch`), `internal/cli/version_mismatch_test.go`, `TestDoctorReportsVersionMismatchInsteadOfStopped`, `TestEnsureDaemonUsesCurrentExecutablePromptsOnVersionMismatch`.

**Bounded Daemon Logging and Event-Driven AXI Runs**

- `internal/logstore` owns all daemon-process byte and retention bounds. Lifecycle output uses `logs/daemon.log`, managed Rovo Dev/OpenCode stdout and stderr use `logs/managed-server.log`, and service bootstrap/direct crash output uses `logs/daemon-bootstrap.log`. Rotation snapshots backups and truncates the current inode in place so held service and child descriptors keep writing to the bounded current file. Regressions: `internal/logstore/rotate_test.go`, `TestDetachedDaemonUsesBoundedDedicatedLogSinks`, `TestManagedServerOutputIsSeparatedFromLifecycleFailureSummary`.
- Successful read-only IPC methods are DEBUG; mutations and stream starts are INFO; every request failure is WARN. AXI run driving is subscribe-first and `internal/cli/run_reconciler.go` is the sole owner of event reconciliation, reconnect, duplicate-event coalescing, and the slow lost-event heartbeat. Do not reintroduce fixed-interval `get_run` polling. Regressions: `TestSuccessfulReadRequestsDoNotLogAtInfo`, `TestRequestLoggingKeepsMutationsAndFailuresVisible`, `TestDriveRun_HealthyWaitStaysWithinRequestBudget`, `TestRunReconciler_*`.

**Bounded Loss-Aware Event Subscriptions**

- `internal/ipc/events.go` (`ClassOf`) is the single event taxonomy: activity is droppable, state is not, control is broker-generated, and an unrecognized type fails safe to state. Brokers and consumers must read loss tolerance from it rather than re-listing event names.
- `internal/daemon/eventmailbox.go` is the single overflow owner: a per-subscriber ring bounded by 64 events and 1 MiB, non-blocking publish (the executor is never stalled), activity as the only evictable class, and everything else folded into one sticky coalescing `stream_gap` that drains ahead of queued payload. A reserved slot is not enough - it fails at the second simultaneous transition - and producer-side channel receives race the reader, which is why the queue is a ring under a mutex.
- Every state event and every `get_run` snapshot carries a monotonic `StateRev`; `runSnapshot` samples it **before** the DB read, which is sound only because every producer writes state and then emits. Consumers apply a delta only when its revision is newer, so a delta queued before a snapshot cannot regress state after it. Every subscription opens gapped, so attach and reconnect always reconcile first.
- The fix-review working-tree diff is the only gate context that is never persisted, so it is served on demand by `ipc.MethodGetStepDiff` (`RunManager.StepDiff`, bounded at 512 KiB) instead of riding the stream: it was the only unbounded payload, and one frame past the 1 MiB transport line limit ends the subscription and hides every later event.
- Regressions: `internal/daemon/eventmailbox_test.go` (A1-A13 plus the byte/count ceilings), `TestRunSnapshot_*`, `TestStepDiff_*`, `TestExecutor_StateEventsAreEmittedAfterTheirDatabaseWrite`, `TestClassOfUnknownEventFailsSafeToState`, `TestRunReconciler_StreamGapForcesOneAuthoritativeRead`, `TestSubscribeOversizedFrameEndsTheStreamAndHidesLaterEvents`, `internal/tui/overflow_contract_test.go`.

**Destructive Daemon Lifecycle Guard (`internal/lifecycle/guard.go`)**

- `daemon stop`, `daemon restart`, and `update` refuse by default while pending/running runs exist (the daemon is machine-wide, so stopping it can fail every active pipeline), list the runs via the shared `lifecycle.Decide`/`lifecycle.RunList` helpers, and require an explicit `--force`. `update -y` answers only the different-executable prompt and deliberately does not bypass this guard.
- A run parked at an approval/fix_review gate (`lifecycle.ParkedAtGate`: `Status == running`, `AwaitingAgentSince != nil`, **and** a step row actually in `awaiting_approval`/`fix_review`) is exempt: a clean stop preserves it and the next daemon start resumes it, so it is never a reason to refuse. The step-row evidence is load-bearing: the awaiting-agent write is best-effort, so a stuck marker alone must never present a run as preserved. `lifecycle.Decide` is the one owner every call site uses; one `splitActiveRuns` pass over the `ParkedAtGate`-plus-plan predicate divides the active runs into the blocking set (what a stop/restart/update would actually disrupt) and the parked complement, and it returns that blocking set plus the notice so `guardDestructiveDaemonLifecycle` and `confirmActiveRunsBeforeUpdate` keep only their writers and message strings. The guard's refusal/`--force` count reads the blocking set only. Exemption is conditional on resumability: every call site passes `steps.AllSteps()` (the installed binary's ordered layout, demo mode included) to `Decide`, which derives the required plan from it, and `lifecycle.StepPlanDrifted` re-counts a parked run whose persisted `runs.step_plan` differs (or is unrecorded) as blocking. The plan check alone is weaker than recovery, so `Decide` also corroborates every parked candidate against `lifecycle.ResumePreconditionsMet` - the one owner startup recovery's `prepareRecoveredRun` calls too (worktree present at `run.HeadSHA` plus `pipeline.ValidateRecoveredRun`, which rejects a gate row still holding an `agent_pid`). A candidate that fails corroboration is blocking, never promised preservation. Extend that owner rather than restating its rules on either side; `internal/lifecycle/lifecycletest` builds the resumable parked fixture every guard test needs. `daemon stop`/`restart` need that check too, because the executable they start back up is whatever is installed at that moment and can have been replaced out of band since the run parked. It proves only that the run matches the plan installed now: `update` additionally swaps the binary, and the incoming layout does not exist at guard time, so a layout change shipped by the new version is not detectable there. `GuardDecision.ParkedNotice` owns the operator-facing preservation promise (its own caption via `lifecycle.RunListWith`, not `RunList`'s "active pipeline runs:"); the separate `lifecycle.ResumingBinary` argument, not the plan, marks a decision as a binary swap and qualifies the printed promise with that limit instead of stating a certainty the guard cannot check. `lifecycle.RunCountWords` is the single owner of count grammar on all three surfaces, and `lifecycle.ActiveRuns` is a plain inspection read with no guard semantics. The guard only returns the notice; callers print it after the daemon has actually stopped (after `daemonStopFn`/`daemonStartFn`, and on the update path after `resetDaemon` succeeds), so a refusal, a failed download, or a failed stop never promises preservation. `update` re-reads the guard immediately before `resetDaemon` (`parkedNoticeAtRestart`), so the sentence describes the state at print time rather than a snapshot taken before a multi-minute download.
- Every invocation of the three commands is logged with caller attribution (PID, PPID, parent command line) via `logLifecycleInvocation` to `<NM_HOME>/logs/cli.log`; this is the incident forensic trail, do not remove or weaken it.
