# AGENTS.md

This file is for agentic coding tools working in this repo.

This repository is a Go CLI app named `no-mistakes`.
The binary entrypoint is `cmd/no-mistakes`; implementation code lives under `internal/`, and the package names there are the layout map (CLI in `internal/cli`, daemon in `internal/daemon`, pipeline and steps in `internal/pipeline`, agent adapters in `internal/agent`, terminal UI in `internal/tui`, shared infrastructure in `internal/git`, `internal/ipc`, `internal/config`, `internal/db`, `internal/paths`, `internal/types`).
Build, test, and release commands are owned by the `Makefile`; read it for the full target list instead of relying on a copy here.

Safest local verification sequence after non-trivial changes:

- `gofmt -w .`
- `make lint` (generated-skill drift check plus `go vet`)
- `go test -race ./...` (the e2e suite is behind the `e2e` build tag and excluded)
- `make e2e` when touching agent integrations, the e2e harness, or recorded fixtures
- `go build -o ./bin/no-mistakes ./cmd/no-mistakes`

**Self-update channel manifest (`internal/update`)**

- `no-mistakes update` reads version metadata exclusively from `channels.json` on the GitHub release-asset CDN (`releases/download/channels/channels.json`), not `api.github.com`; a token is never required. Publisher: `cmd/publish-channels`, invoked from `.github/workflows/publish-channels.yml` (reusable `workflow_call`, plus `workflow_dispatch` / `on: release` backstops). `release.yml` calls it after `finalize` because GitHub does not cascade `GITHUB_TOKEN` `release` events, so release-please (pre)releases would otherwise leave the channel stale. Regressions: `internal/update/channels_test.go`, `workflow_publish_channels_test.go`, `TestReleaseWorkflowCallsPublishChannelsAfterFinalize`.

**GitLab Backend (`internal/scm/gitlab`)**

- The backend is pinned against `glab v1.5x`, whose flag surface drifts between versions: the auth check must be host-scoped (`--hostname <host>`, falling back to unscoped only when the host is unknown), `glab mr list` no longer accepts `--state opened`, `glab mr update` has no `-y`/`--yes` flag at all (unlike `mr create`, which does, so `UpdatePR` must not pass it), and the daemon's detached-HEAD worktree breaks `glab ci get`, so pipeline jobs are read via the branch-independent `glab api .../pipelines/<id>/jobs` REST endpoint.
- The comments in `internal/scm/gitlab/gitlab.go` own the full rationale for each trap; extend them there when you hit new glab version drift.

**Gitea Backend (`internal/scm/gitea`)**

- Verified empirically against a real `tea 0.15.1` CLI and a real Gitea 1.27.2 + Actions instance (Docker/Podman `gitea/gitea` + `gitea/act_runner`), not guessed from docs. `tea whoami` has no `--login` flag (unlike every other tea entity subcommand), so `Host.Available` scopes its check through `tea api --login <name> /user` instead - the same host-scoping purpose as glab's `--hostname`.
- `tea actions runs view --jobs --output json` does NOT emit clean structured JSON: `--output json` renders the run header as plain text and only the trailing jobs array is real JSON, and that array carries `status` (queued/in_progress/completed) but no `conclusion` (success/failure/...) at the job level. Job-level pass/fail is read from the REST endpoint (`GET /repos/{owner}/{repo}/actions/runs/{run}/jobs`, which does carry `status` + `conclusion`) reached through `tea api`, which reuses tea's own stored login/token - no separate HTTP client or credential needed.
- `tea pulls list --output json` renders every field (including `index` and `mergeable`) as a JSON *string*, while `tea pulls <idx> --output json` (single-PR view) renders the same fields with native JSON types (`index` an int, `mergeable`/`hasMerged` bools). The two response shapes are genuinely different structs in `gitea.go`; do not unify them.
- `tea pulls create` has no `--output json` flag and echoes the PR body into its human-readable stdout, so a body containing an `http(s)://` URL can defeat a naive "first URL line" scrape. `CreatePR` re-lists the PR by head branch via `tea pulls list` for a structured result instead of parsing create's own output; scraping stdout is only a last-resort fallback.
- `tea pulls edit` has no `--base` flag (unlike `tea pulls create --base`). Retargeting uses `tea api --method PATCH --field base=<branch>` on `/repos/{owner}/{repo}/pulls/{index}`; omitting `--method` would POST because a body defaults tea api to POST. `FindPR` copies `item.Base` onto `scm.PR.BaseBranch` so a per-run override can see the live forge base.
- tea infers "which Gitea instance" from the current directory's git remote, which the daemon's detached bare-gate repo never has, so every invocation carries `--login <name>` explicitly. The login name is resolved from tea's own `config.yml` by host (`scm.ResolveGiteaLogin`), mirroring `glabKnowsHost`/`ghKnowsHost` for detection.
- `Capabilities().MergeableState` is declined (matching Bitbucket): Gitea's PR `mergeable` field has a documented upstream bug (go-gitea/gitea#25849) that can stick `false` after a conflict is actually resolved.
- `tea actions runs list`'s array order is not documented as newest-first, and a branch can have more than one run sharing the same head SHA (e.g. a manual UI re-run), so `GetChecks`/`FetchFailedCheckLogs` select the run via `mostRecentRun` (highest numeric run ID) rather than trusting list order or index `[0]`.
- The comments in `internal/scm/gitea/gitea.go` own the full rationale for each trap.

**OpenCode Adapter Failure Reporting (`internal/agent/opencode*.go`)**

- opencode reports a failed turn on `info.error` with an HTTP 200 and no parts, and serializes every named error as `{"name": ..., "data": {...}}` - the payload fields are nested under `data`, never at the top level. Decoding only the flat shape silently blanks the message, and ignoring non-`StructuredOutputError` variants drops the cause entirely so the run reports the undiagnosable `opencode returned no text output`. `opencodeMessageError` owns the wire shape and `opencodeMessageFailure` owns the surfaced error.
- Retry is opencode's call, not ours: `classifyOpencodeTransient` trusts `data.isRetryable` (status class only as a fallback) and deliberately does not fall through to the shared substring matching, so a 400 quoting a provider's rate-limit prose is never retried. Regressions: `TestOpencodeAgent_FailedTurnSurfacesProviderErrorInsteadOfEmptyOutput`, `TestOpencodeAgent_StructuredOutputErrorReadsNestedErrorData`, `TestOpencodeAgent_RetriesRetryableProviderErrorThenSucceeds`, `TestClassifyOpencodeTransient`.
- A retryable verdict is necessary but not sufficient: `runOnce` creates a FRESH session per attempt, so retrying a turn that already invoked a tool replays its side effects with no memory of them. `classifyOpencodeTransient` withdraws the retry when `opencodeTurnRanTools` saw a `tool` part on the SSE stream (`opencodeStreamState.toolInvoked`, durable - not the cosmetic `pendingStepSeparator` that `step-finish` sets and every emit clears) or in the message response body. Resuming the session instead was rejected: opencode's message endpoint only appends another user message, so whether the model re-runs the tool stays its judgement rather than a guarantee. `step-finish` alone is never tool activity - every turn emits one - and the blip this retry exists for kills the turn before any tool runs, so it is unaffected. Regressions: `TestOpencodeAgent_RetryableFailureAfterToolActivityIsNotRetried`, `TestOpencodeAgent_RetryableFailureWithoutToolActivityStillRetries`, `TestOpencodeAgent_ToolPartInTheMessageResponseAlsoBlocksRetry`.
- The general `info.error` branch in `runOnceWithFormat` must stay AFTER the `isThinkingToolChoiceConflict` check: that conflict is the trigger for the prompt-only structured-output fallback, and a general failure claiming it first silently disables the fallback.
- That fallback is a second attempt in a fresh session too, and a `session.error` can arrive at any point in a turn, so it carries the same gate: `thinkingConflict` annotates the trigger with `errOpencodeToolsAlreadyRan` when the turn ran a tool and `runOnce` then reports the conflict instead of falling back. Regression: `TestOpencodeAgent_ThinkingConflictAfterToolActivityDoesNotFallBack`.
- `opencodeMessageError.rawData` keeps the verbatim `data` payload beside the typed `Data`, because thinking/tool_choice detection scans the payload as text (`providerText`) and a decode into the typed struct drops every provider-specific extra it has no field for.

**Claude Code Workspace Trust (`internal/claudetrust`)**

- Claude Code discards a repo's project-scoped permission entries when the workspace carries no `hasTrustDialogAccepted` in `~/.claude.json`. The workspace it keys on is the BARE gate repo `paths.RepoDir(<repoID>)` (`<hash>.git`), not the run worktree the agent has as CWD: Claude Code walks up for the git root, resolves a linked worktree's `.git` file to its commondir, and keeps the commondir when its basename is not literally `.git`. It stores that key realpath'd and NFC-normalized, so every comparison goes through `claudetrust.CanonicalWorkspace` or a symlinked `NM_HOME` reads as untrusted.
- Most of what gets discarded is inert here. `buildArgs` adds `--dangerously-skip-permissions` unless the operator pinned a permission mode, and under that bypass a dropped `permissions.allow`/`ask`/`deny` entry changes nothing. Only `permissions.additionalDirectories` still costs the run, because bypass grants approval rather than extra read roots. `Warning.BitesUnderBypass` owns that split and answers false for an unnamed category, since a false abort kills a working run.
- The stderr detector is best effort: the `console.error` that prints the warning is conditional in the binary, so entries can be dropped silently. `internal/cli/doctor.go` `doctorClaudeWorkspaceTrust` is the standing check, and it only ever warns because doctor cannot establish the daemon's `HOME`/`CLAUDE_CONFIG_DIR` or each repo's trusted-branch `agent`.
- The package is read-only by hard constraint: it must never write a trust decision into `~/.claude.json`.

**Live-Validation Contract (Test step)**

- The Test step's evidence turn returns `scenarios` (name, result pass/fail/untested, `live`, evidence, reason) plus a `verdict` (go/no-go/inconclusive/no-surface); both are REQUIRED by `testFindingsSchema` and validated in `unmarshalRequiredTestFindings`. `live: true` means driven against the real running product in that run - a unit test, stub, or fixture is not live.
- Invalid analyzer output is not a fatal run error on the first attempt: `runTestAnalyzer` gives a fresh agent the rejected payload and validation errors for a bounded correction (`testAnalyzerMaxAttempts`); only exhausting that bound fails the step. The correction prompt must remain correction-only: no tools, scenario reruns, or external operations; preserve supported observations and downgrade unsupported pass/fail claims to untested. Do not weaken the pass/fail-must-be-live or untested-must-have-a-reason invariants to avoid the retry.
- Verdict policy (captain's call C2 = a, plus the 2026-09-07 no-surface ask-user decision) lives in `verdictFindings` (`internal/pipeline/steps/test.go`): `no-go` parks as an auto-fixable error, `inconclusive` parks as an ask-user warning (live surface, too little driven), `no-surface` parks as an ask-user warning when the change has nothing no-mistakes can drive live, a `fail` scenario with any other verdict is rejected as a contract violation, `no-surface` with any live or pass/fail scenario is rejected so a skipped live validation cannot masquerade as no-surface, and `untested` NEVER parks - it is listed on the PR so reporting it honestly stays cheaper than guessing a pass. Do not make untested blocking.
- Rendering is owned by `internal/pipeline/steps/prsummary_scenarios.go` (Testing section, Pipeline fold, and attestation `live_validation: {verdict, live, total}`). The attestation omits `live_validation` whenever the current head differs from the head Test validated. Pre-contract runs parse and render exactly as before.
- The evidence turn is unconditional: a green `commands.test` baseline is never enough on its own, so the step always drives scenarios afterwards. The step deliberately owns no capability inventory, scratch lab, or environment exports - the agent discovers what the machine can do for itself.
- `test.instructions` is the repository's live-validation runbook. It is trusted-default-branch-only, exactly like `document.instructions` and for the same reason (it steers the gate that validates the pushed branch), and is resolved from the repository only - never from global config, which has no repository to describe.
- Regressions: `TestTestStep_PromptDerivesScenariosAndMarksLive`, `TestTestStep_VerdictPolicy`, `TestTestStep_NoLiveSurfaceCIWorkflowAsksUser`, `TestTestStep_MissingScenarioContractFails`, `TestTestStep_InvalidAnalyzerPayloadTriggersCorrectionRound`, `TestTestStep_InvalidAnalyzerPayloadExhaustsCorrectionBound`, `TestTestStep_ValidMixedPayloadDoesNotRetry` (`internal/pipeline/steps/test_scenario_contract_test.go`), `internal/pipeline/steps/prsummary_scenarios_test.go`, `require_no_mistakes_live_validation_test.go`, `TestEffectiveRepoConfig_TestInstructionsTrustedOnly`.

**Review Schema Retry (`internal/pipeline/steps/review.go`)**

- When the agent adapter marks a review turn's final output as rejected against the schema (`agent.IsStructuredOutputRejected`: Pi when its final JSON fails validation, opencode once its own internal StructuredOutput retries run out), or `parseReviewAnalyzerOutput` refuses the output, that is a formatting slip, not a verdict: `ReviewStep.Execute` reruns a fresh, session-free review of the same prompt plus a note quoting the validation error, up to `reviewAnalyzerMaxAttempts` (3) attempts in total.
Claude Code's `--json-schema` re-prompts within its own limit and reports exhaustion as `error_max_structured_output_retries`; that result is deliberately not marked as a rejection and fails the step as before, so there is no second retry layer and Test's correction loop is untouched.
Findings come only from the attempt that validates; nothing else from a rejected attempt carries over, and fix-mode turns are never retried.
Exhausting the bound fails the step with `validate review analyzer findings after 3 attempts: <last error>`, so an unreadable review never passes (issue #703); the unconfigured "pass" meaning is unchanged.
- Every other failure returns at once, and so does a rejection from a turn its deadline or a cancellation cut short (`agentInvocationError` carries both the adapter's rejection and `errReviewAgentTimeout`). This is a rerun of the review, not a correction turn; Test's correction behaviour is separate and unchanged.
- Eval replay (`internal/eval/replay.go` `observedAgent`) sums token usage across every review attempt and reports none when any attempt lacks reported usage, matching the captured baseline, so a candidate that needed reruns never reads as cheaper.
- Regressions: `internal/pipeline/steps/review_schema_retry_test.go`, `TestReviewStep_UnrunAnalyzerDoesNotApprove`, `TestReplayTokensCoverEveryReviewAttempt`, e2e `TestAnalyzerEvidenceFailuresFailPipelineJourney`.

**CI Step Findings Model**

- `CIStep.Execute` has the review step's shape: a fix round (`sctx.Fixing`) first repairs the findings the executor selected (`repairFromFindings`, `internal/pipeline/steps/ci_fix.go`), then the monitor runs; every settled observation (all checks finished, every authorized transient rerun spent, at least one issue) returns one finding per issue with its action (`ciObservationFindings`, `ci_findings.go`) and the executor's shared loop decides what follows. The step never counts or limits fix rounds; `auto_fix.ci` is enforced by the executor from the round history, which survives `ResetStepsFrom` and daemon restarts. `step_results.ci_fix_attempts` is retired (column kept, never read).
- Classification reads provider structure only: a job verdict (fail bucket) and a merge conflict are `auto-fix` errors; an unresolved transient is `ask-user` (`unresolvedTransientFindings`); a check whose `scm.Check.App` (GitHub `checkSuite.app.slug`) is in `scm.ReviewBots` (Greptile: `greptile-apps`) becomes one `ask-user` warning per unresolved bot comment, bounded (`maxReviewBotCommentFindings`), so it never spends a round. An empty `App` is never a bot. The fix agent, not metadata, decides whether an unknown red is about the code: its `code_change_needed=false` conclusion parks the selected findings as `ask-user` (`ciRepairParkOutcome`).
- `types.Finding.Check` (display name), `types.Finding.CheckID` (provider identity), and the `FindingCategoryCI*` constants are the routing keys the fix half reads (`parseCIFixTargets`); `Finding.UnmarshalJSON` and `findingWire` copy fields explicitly, so a new field must be added there or it drops on every parse. Findings ride the IPC event stream, so per-comment findings stay bounded.
- A published repair keeps monitoring inside the same fix round and must call `sctx.MarkRunning()` (executor-owned: durable status back to `running` plus a `step_started` event), or the step stays `fixing` and neither the TUI nor `axi`'s `checks-passed` (`ciReadyToMerge` requires `running`) can surface. The post-repair stale-evidence guard is `lastRepairStillUnverified`: selected checks are snapshotted before a resumed repair, and targets that remain red with neither a newer completion/execution discriminator nor an observed pending state keep the monitor waiting instead of re-escalating. Findings deferred by a fix round survive pending observations and terminal monitor errors until a fresh settled issue set or an established clean result supersedes them.
- Regressions: `TestCIStep_GreptileOnlyRedParksAsAskUserAndSpendsNoAutoFixRound`, `TestCIStep_MixedGreptileAndTestFailureRoutesOnlyTheTestToAutoFix`, `TestCIStep_PublishedRepairResumesMonitoringAndWaitsForTheRerun`, `TestCIResumedRepairSnapshotsSelectedCheckCompletion`, `TestTerminalFailureFreshnessUsesExecutionIDWithoutCompletionTime`, `TestCIStep_PersistentCheckReadFailureParksAtAskUser`, `TestCIStep_UserFixOfTransientFindingIsHonored`, `TestCIObservationFindings_ClassifiesEachIssueByProviderStructure`, `TestExecutor_MarkRunningReturnsAFixingStepToRunning`, `TestExecutor_RestartsValidationFromRequestedStep`, `TestGetChecksCarriesCheckSuiteAppSlug`, `TestParseFindingsJSON_RoundTripsCICheckFields`. Step tests drive the loop with `stepstest.ExecuteWithAutoFix` (the executor's auto-fix loop in miniature); a test that calls `Execute` once sees only the observation.

**Rebase Step Integration Shape (`rebase.strategy`)**

- `rebase.strategy` (`rebase` default, or `merge`) selects how the rebase step integrates a moved base. Under `merge` each target is merged with `git merge --no-ff` instead of rebased onto, so the reviewed head stays on the branch as the merge commit's FIRST parent. Three things follow and are what the option exists for: `ciRepairContinuityGap`'s ancestry test then passes natively (no patch-id or content guess), publication is a fast-forward, and the merge commit's two parents keep a conflict resolution auditable from outside the pipeline afterwards. To match, `mergeWithAgent`'s resolver prompt requires an ADDITIVE resolution, which `rebaseWithAgent`'s "minimal necessary changes" prompt deliberately does not; do not unify the two prompts.
- `mergeWithAgent` PROVES the merge instead of trusting the agent's conclusion, and target ancestry alone is not that proof (a rebase satisfies it too). It snapshots the pre-merge head and resolves the target to a SHA BEFORE `git merge` runs - resolving by refname afterwards lets an agent that fetches mid-resolution fail a merge that actually landed - and afterwards requires HEAD to have moved off the pre-merge head with BOTH snapshots ancestors of it. `shouldSkipRebase` has already consumed every non-divergent case, so two divergent commits can only both be ancestors of HEAD through a merge commit; that admits a follow-up commit on top of the merge while still rejecting `merge --abort`, a rebase, and `reset --hard` onto the target, and an unrelated commit made after abandoning it. A conflicted rebase is the other mid-operation state the worktree can be left in and git sets no `MERGE_HEAD` for it, so `rebaseInProgress` is checked alongside `mergeInProgress` and a leftover rebase is aborted and rejected too. Every rejection routes through `restorePreMergeHead`, which resets the worktree back to the head that merge started from before returning so a rejected attempt is never left checked out as the branch's state, and is fail-closed: a restore that does not land exactly there, or that leaves a rebase in progress underneath it, is reported inside the returned error. Regressions: `TestRebaseStep_MergeStrategyUnconcludedMergeIsAbortedAndFails`, `TestRebaseStep_MergeStrategyConflictedRebaseLeftInProgressIsAbortedAndFails`, `TestRebaseStep_MergeStrategyAbortedMergeFails`, `TestRebaseStep_MergeStrategyRebasedInsteadOfMergedFails`, `TestRebaseStep_MergeStrategyUnrelatedCommitInsteadOfMergeFails`, `TestRebaseStep_MergeStrategyResetOntoTargetFails`, `TestRebaseStep_MergeStrategyFollowUpCommitAfterTheMergeIsAccepted`.
- The flag is trusted-default-branch-only regardless of `allow_repo_commands`, for the same reason `no_ci` is: a pushed branch must not opt its own integration out of the evidence shape the maintainer chose, in either direction. An unrecognized value fails the config closed rather than falling back.
- `forcePushDecision.fastForward` is a separate, unconditional path: an append-only update publishes with a plain push, no `--force`, so the remote rather than our lease bookkeeping enforces the no-rewrite property. It applies under either strategy.
- `test`/`ci` scope is deliberately untouched: both still run in full on the integrated head, and `ci_fix.go`'s merge-conflict repair still rebases and therefore still always revalidates.
- User-facing semantics are owned by `docs/src/content/docs/reference/repo-config.md` (`rebase.strategy`). Regressions: `internal/pipeline/steps/rebase_merge_test.go`, `internal/config/rebase_strategy_test.go`, `TestResolveForcePushDecision_FastForwardNeedsNoForce`, `TestResolveForcePushDecision_RewriteIsNotAFastForward`.

**Repo Config Trust Boundary (security)**

- The daemon runs `commands.*` from `.no-mistakes.yaml` verbatim via `sh -c`, and `agent` selects which process launches with the maintainer's credentials. The code-executing selection fields (`commands.{prepare,test,lint,format,metrics}`, `test.units[].command`, and `agent`) are therefore loaded from the trusted default branch at a **pinned SHA** resolved by a fresh fetch, never from the pushed SHA. The run aborts when the trusted commit or its present config cannot be read and parsed; a readable tree with no config is valid. See `internal/daemon/manager.go` `startRun`, `loadTrustedRepoConfig`, and `assertGateTrustedConfigReadable`.
- `document.instructions` (the repo's documentation placement policy), `test.instructions` (the repo's live-validation runbook, see Live-Validation Contract above), `test.allow_approve_over_failure` (the recorded reason that opts require-no-mistakes into accepting a Test step approved over a failing `commands.test`), `review.path_instructions` (path-scoped review guidance appended to the review prompt), `gates` (extra repository-declared checks), `disable_project_settings` (the gate-agent project-instruction opt-out), `no_ci` (positive declaration that the repository intentionally has no CI), `skip_steps` (the standing form of `--skip`, additive with a run's own selection via `Config.SkippedSteps`; an unknown step name fails the config), `restart.exempt_paths` (the glob list that lets a docs-only agent commit skip re-entering validation, see the Agent-Authored Commits Re-Enter Validation section; regression: `TestEffectiveRepoConfig_RestartExemptPathsTrustedOnly`), `pr.template` (path and pinned bytes), `pr.publish_intent`, the whole `ci` block, and the whole `metrics` block are also trusted-only, regardless of `allow_repo_commands`: a pushed branch must not weaken any of those boundaries, self-declare no-CI to bypass checks, steer its own review or its own live validation, raise the maintainer-funded `ci.rerun_transient` budget, turn off required post-repair revalidation (`ci.revalidate_repairs`), waive the required check for an approved-over-failure test command, or raise the `metrics.threshold` that judges its own breach. The `metrics` block sits on the trusted side whole rather than field by field, so a `metrics.*` field added later lands on the safe side by default; copy it the way `Restart` is copied and clone `ExemptPaths`, since a bare struct copy aliases the trusted slice. Regressions: `TestEffectiveRepoConfig_MetricsBlockTrustedOnly`, `TestEffectiveRepoConfig_MetricsBlockOptInStillUsesTrustedValue`, `TestEffectiveRepoConfig_MetricsBlockNoTrustedCopyIsZeroed`, `TestEffectiveRepoConfig_TestInstructionsTrustedOnly`, `TestEffectiveRepoConfig_AllowApproveOverFailureTrustedOnly`. The operator's global CI settings are a separate, non-contributor surface that trusted repo values override. Enabling the commands opt-in must not drop the maintainer's own trusted values. When the project-settings opt-out is enabled, only adapters with verified effective suppression may launch. Other non-executing fields (`ignore_patterns`, `auto_fix`, `commit`, `intent`, and the rest of `test`) are still read from the pushed branch, with exactly two exceptions inside them. `auto_fix.min_severity` is trusted-only, because the retry counts beside it only bound effort while the severity floor is a gate strength a pushed branch could raise to suppress automatic fixing of its own warnings (regression: `TestEffectiveRepoConfig_AutoFixMinSeverityTrustedOnly`). `test.units` sits in the `commands.*` group instead of the surrounding `test` block, because each unit carries a `command` the daemon runs verbatim, so it honors `allow_repo_commands: true` exactly as `commands.*` does and is otherwise trusted-default-branch-only. `commands.prepare` and `commands.metrics` are plain members of that group and inherit `commands.test` semantics with no new code (regressions: `TestEffectiveRepoConfig_CommandsMetricsTrustedOnly`, `TestEffectiveRepoConfig_CommandsMetricsOptInUsesPushedValue`).
- Selecting which trusted config applies to a run must never depend on a pushed-branch field. `review.path_instructions` is matched against the COMPLETE changed-file set, never the `ignore_patterns`-filtered subset, because filtering there lets a contributor suppress a maintainer's rule from their own review by ignoring its glob. `reviewablePaths` (`internal/pipeline/steps/common_diff.go`) answers only "does this run have anything to work on".
- Exactly ONE `.no-mistakes.yaml` is trusted per run. Under the operator's global `trust_working_path_config` opt-in, `applyWorkingPathTrustedConfig` (`internal/daemon/manager.go`) promotes a copy read from `repos.working_path` - the daemon-host primary checkout, never the gate worktree a contributor pushed to - to be that file, and `config.ResolveWorkingPathTrusted` REPLACES the pinned-SHA copy with it rather than layering: a field the working-path copy leaves out is unset, not inherited, because composition cannot express retiring a default-branch command. An absent working-path file changes nothing. It exists for gated repos whose default branch is owned by a team that does not run no-mistakes, so there is nowhere trusted to commit commands. Two boundaries survive replacement, both refusals to weaken: `allow_repo_commands` stays on the default-branch side (a local file can neither enable pushed-branch commands nor retract the default branch's opt-in), and `disable_project_settings` is true-wins. A parse failure keeps the trusted copy, and a git-tracked working-path file warns (a branch checkout there can change trusted commands) but still applies. Regressions: `internal/config/config_workingpath_trust_test.go`, `internal/daemon/manager_workingpath_trust_test.go`.
- `pr.base_branch` (the PR, rebase, and CI-merge-conflict-auto-fix integration branch, falling back to `Repo.DefaultBranch` when unset) is trusted-default-branch-only, but unlike the fields in the bullet above it is the deliberate exception that also honors the `allow_repo_commands: true` opt-in, since it controls where an already-maintainer-authorized PR lands rather than what executes. Once a PR already exists, its actual forge base branch (read live via `scm.PRBaseBranchReader`) is authoritative for CI merge-conflict repair and base-branch tip monitoring over a since-changed `pr.base_branch`, and PR lookup matches the existing PR by branch alone, never filtered by base, so a later config change updates that PR instead of opening a duplicate against the new base. Full semantics are owned by `docs/src/content/docs/reference/repo-config.md` (`pr.base_branch`). Regressions: `TestEffectiveRepoConfig_PRBaseBranchTrustedOnly`, `TestEffectiveRepoConfig_PRBaseBranchOptInUsesPushedValue`, `TestEffectiveRepoConfig_PRBaseBranchOptInWithNoTrustedCopyUsesPushedValue`, `TestLoadRepoConfig_PRBaseBranchRejectsInvalidBranchName`, `TestLoadRepoConfig_PRBaseBranchEmptyIsValid`, `TestPRStep_UsesConfiguredBaseBranch`, `TestRebaseStep_UsesConfiguredPRBaseBranch`, `TestCIStep_AutoFixUsesExistingPRBaseAfterConfigChanges`, `TestPRStep_ExistingPRAgainstDifferentBaseIsUpdatedNotDuplicated`.

**Parked / Awaiting-Agent Signal**

- Recovery has two resume points, and `pipeline.resumePoint` (`internal/pipeline/executor.go`) is the discriminated shape holding exactly one: an approval/fix-review gate, or a live CI monitor. `lifecycle.ParkedAtGate` owns the gate predicate alone; `lifecycle.ResumableCIMonitor` (`internal/lifecycle/cimonitor.go`) owns the CI predicate (only active step is `ci`, `running`, no `agent_pid`, run has a PR URL) and is checked independently, not folded into `ParkedAtGate`. The `agent_pid` clause is not redundant with the status: the CI step runs its auto-fix agent inline from inside `Execute`, and the executor only writes `fixing` for an outcome marked auto-fixable, which a CI outcome never is, so a live repair keeps the row `running` with the agent's pid recorded against it. The wider `lifecycle.CIMonitorRun` deliberately ignores the pid, because the SQL lift in `db.failActiveRuns` it mirrors does.
- Preserving a CI monitor across a clean stop is conditional, and `Executor.ciMonitorPreservable` owns every condition: a re-read `running` `ci` row with no `agent_pid`, a freshly read non-blank PR URL, a worktree with nothing uncommitted in it, and a worktree head equal to the run's recorded head. The head check is `lifecycle.WorktreeMatchesRun`'s own rule read at stop time, so a stop never promises a resume the next start refuses: `steps.commitRepair` commits before `recordRepair` writes the new head, so a stop in that window finds a clean worktree one commit ahead. Keep recovery's rule strict rather than accepting a descendant; on the gate-parked path a descendant head is the adverse evidence it exists to catch. That check is a second copy of the owner's rule rather than a call into it, because `lifecycle` imports `pipeline`; the two known differences are that the owner resolves the checkout through `worktrees.RecordedDir` while this takes a resolved `workDir` and trims both sides, and that the owner reports a failed read as unavailable evidence while every refusal here is non-preservable. EVERY refusal, incomplete read and completed adverse fact alike, routes through the single wrap in `ciMonitorPreservable` (the facts live in `ciMonitorPreservationRefusal`); keep that structural so a refusal added later cannot land on the destructive side by omission. The wrap applies `pipeline.ErrCIMonitorInterrupted` only when the run holds a PR URL (`runReachedItsPR`, which answers yes on a failed read), and `failRun` then ends the run as `types.RunCIMonitorInterrupted` under that concrete reason rather than the cancellation cause, so `RunManager.removeRunWorktree` spares the checkout. Failing closed must never cost the worktree of a run that reached its PR: a dirty or unreadable checkout can hold a repair commit an earlier round already made and never published. A refusal on a run with no PR URL ends as an ordinary failure and its checkout is reclaimed, because nothing was pushed for a monitor to poll and the status names an open PR that outlived the run. The dirty check is the one the pid cannot cover, because every adapter emits its exit event on a cancelled turn and the executor clears the pid, and `ci.go` swallows the failed repair as a warning; preserving those half-written edits would let the next repair's `git add -A` commit them under a message describing a different repair. Every read there fails closed and logs the refusal, so an unpreservable step fails now rather than leaving a row the next start declines and the blanket sweep then reports as a crash. The cleanliness rule itself has ONE owner, `pipeline.CIMonitorWorktreeClean`, and every site deciding the question reads it: the stop path, the destructive guard and startup recovery through `lifecycle.ResumePreconditionsMet` (which takes the run's step rows and applies the clause on the CI branch alone), the drain through `lifecycle.PreservableCIMonitor`, and the startup orphan sweep in `skipWorktreeCleanup`, whose head-equality rule alone would reclaim a checkout holding an interrupted repair's uncommitted work. It lives in `pipeline` because `lifecycle` imports `pipeline` and the dependency cannot be reversed. A read that does not complete comes back as `ErrRecoveryEvidenceUnavailable`, so recovery defers on it while a completed dirty read is adverse; no site treats either answer as clean, and none costs the run its worktree. **AXI Run Resolution Is Branch-Scoped (`resolveRun`)**

- `axi status` and `axi logs` resolve an implicit run from the caller's current branch only: its active run, else its most recent one, else nothing.
There is deliberately no repo-wide "most recent run" fallback - one clone routinely has several worktrees on different branches, and that fallback reported one worktree's terminal run to every other worktree under the same `run:` key a run of the caller's own gets, which reads as "your work failed" while the real pipeline is mid-flight.
A detached HEAD owns no branch, so it resolves nothing either.
- Deliberate cross-branch inspection is `--run <id>`. When the caller's branch is known and differs, `axi status` renders the selected run under `other_branch_run:` plus a top-level `current_branch:` - reusing the home view's `other_branch_active_run` vocabulary - so a consumer keyed on `run:` cannot pick up a run proven to be on another branch. An explicit run selected while the caller's branch is unknown stays under `run:` because no branch relationship is proven.
- Labels and commands use separate evidence rules: branch-scoped `axi respond` help is safe only for implicit current-branch resolution. Every explicit `--run <id>` selection is observation-only, even when its branch matches the caller's, because a newer active run on that branch could receive the bare response command instead; its gate stays visible and every log command retains `--run <id>`.
The rationale lives in the `resolveRun` doc comment and the status-rendering comments (`internal/cli/axi_query.go`).

**Test Discovery and Execution (`internal/pipeline/steps/test_discovery.go`, `test.go`)**

- The Test step splits into discovery (`discoverTestUnits`) and execution so a green result names the units it covered. Precedence: a configured `test.units` layout, then `commands.test` as one implicit `repository` unit, then an agent inference pass. Only the first two get the trusted/opt-in treatment `commands.test` already has (see the Repo Config Trust Boundary section); the agent path reads the pushed worktree. `sctx.Config.TrustedConfigSHA` is available to a step, so the trusted commit is reachable; what is missing is a trusted-TREE reader (`git.ShowFile` reads one path, and nothing lists or checks out a tree at a SHA). The guard runs after the under-selection expansion and BEFORE the evidence pass, so no agent turn is spent on a run that already failed it, and not at all when no unit command ran, which is the agent-evidence path. A change touching no file whose extension the profiles describe skips the changed-function requirement alone, or every README edit parks.
- Coverage never enters the branch and is never published. `RunManager.cleanupRunCoverage` drops the run's directory when it finishes and `sweepOrphanCoverageDirs` drops what a crash left, sparing every active run and sweeping nothing when the active-run list cannot be read, the same posture `recoverableParkedRuns` takes toward that read. A second under-selection fault in the same run (`RunShared.NoteTestScopeFault`) parks instead of expanding again: a repeat means discovery itself is unreliable, not merely incomplete this once.

The count is always the true total. Regression: `TestTestStep_GreenAttemptReportsTheDroppedChangedFileList`.
- Discovery narrows what the evidence pass re-runs, never whether it happens: the pass is unconditional (see Live-Validation Contract above), so a configured layout, an inferred one, and no unit at all all reach it. When the selected units' commands already ran this attempt, the prompt tells the agent to read and judge those results and not to widen past the selection. **Metrics Step (`internal/pipeline/steps/metrics.go`, `metrics_verdict.go`)**

- The step is generic: it runs `commands.metrics`, reads a verdict, and gates. The command that computes CRAP is out of scope here and lives in the `coding-standards` repository, so `metrics_verdict.go` defines the contract that command must meet. There is deliberately NO agent fallback for an empty command, unlike Lint and Document, because a CRAP score needs measured complexity joined to measured coverage and an agent producing those numbers by inspection is producing fiction.
- The verdict is read from STDOUT ALONE, captured apart from stderr through `runStepShellCommandEnvSplit`. A single combined pipe interleaves stderr into any report longer than `PIPE_BUF`, and a corrupted report fails OPEN onto the exit code. Both streams still reach the log and the failure output. Regression: `TestMetricsStep_StderrDoesNotCorruptTheReport`.
- Parsing tries the whole trimmed stdout, then makes ONE linear pass over ALL of it, matching braces with a STACK and recording every balanced object AT EVERY DEPTH (string literals and their escapes skipped; a raw newline also ends a string, since JSON forbids one inside, which resynchronises the scan after a stray quote in a log line), then tries the recorded objects newest first. Three earlier rules each lost a real report: scanning backwards from every `{` spent a fixed candidate budget on the report's own per-function entries; recording only TOP-LEVEL objects jumped straight over a report nested in a balanced wrapper; and cutting stdout to a fixed tail severed the opening brace of any report bigger than the cut. Work is bounded by `maxMetricsReportCandidates`, the most recently closed objects, never by cutting the input. That bound evicts the OLDEST candidate, and a report is usually early relative to trailing per-file progress output, so only objects whose text contains `metricsFunctionsKey` are recorded at all: `decodeMetricsReport` rejects every other candidate anyway, so a log object took a slot for nothing and a long enough log stream evicted the real report and passed a breaching repository on exit 0. "Last line that parses" is wrong for this input too: most tools pretty-print, so no single line parses, and it preferred a trailing debug dump over the real report. A candidate counts as a report only when the `functions` key is present; `null` counts as present and means zero measured functions. Regressions: `TestEvaluateMetricsOutput_ALongReportAfterALogLineStillParses`, `..._AReportNestedInABalancedWrapperStillParses`, `..._AReportLargerThanTheOldTailBoundStillParses`, `..._TrailingLogObjectsDoNotEvictTheReport`.
- A reported `file` is normalised to the repository-relative form ONCE, in `evaluateMetricsOutput` where the report is read, so the exemption match, `Finding.File`, and the `metrics.json` breach record all read the same string. The analyser names the file however it likes and absolute paths are the common default, and `publishRunEvidence` pushes `metrics.json` to the orphan evidence branch with no redaction of file contents, so normalising inside the exemption check alone leaked the daemon host's worktree path into a pushed branch. `metricsWorkDirRoots` resolves the worktree once per report and carries the symlink-resolved form beside it, because the strip is a literal prefix match and macOS names one worktree both `/var/...` and `/private/var/...`. Regressions: `TestMetricsStep_AbsoluteReportedPathIsPublishedRepositoryRelative`, `TestMetricsStep_SymlinkedWorktreeStillPublishesRepositoryRelativePaths`.
- Every `metrics.exempt_paths` entry runs through `validatePathInstructionGlob`, exactly as `restart.exempt_paths` does: `matchIgnorePattern` answers false for a pattern `path.Match` rejects, so an unvalidated malformed waiver is inert and the run parks on the very file the maintainer exempted. Regressions: `TestValidateMetricsRaw`, `TestLoadRepoConfig_MalformedMetricsExemptGlobFailsTheLoad`, `TestLoadRepoConfig_ValidMetricsExemptGlobStillLoads`.
- A pass carries findings too: a `warning` item, never a park, when the output did not parse (nothing was measured, so the exit code alone made that green) and when `changedFilesEnvValue` dropped part of the changed-file list. Regressions: `TestMetricsStep_PassingUnparseableOutputCarriesAWarningFinding`, `TestMetricsStep_GreenAttemptReportsTheDroppedChangedFileList`.
- Every finding this step emits carries an explicit ID, because `types.FilterFindings`/`ExcludeFindings` key on it and a blank one is reachable only by the positional ID `NormalizeFindings` assigns, which moves with the list around it. A breach ID is derived from the file and function (`metricsBreachID`), never from its index: the list is sorted by score, so a positional ID retargets a different function as scores move and an operator's `--findings` silently decides the wrong one. Regressions: `TestMetricsBreachFindings_IDsAreStableAcrossAReorder`, `TestMetricsBreachFindings_EveryItemCarriesAnID`.
- The changed-file omission advisory is ONE helper, `changedFilesEnvAdvisory` beside `changedFilesEnvValue`, shared with the Test step and carrying `ask-user`: a command that read a short list measured the wrong scope, which is the operator's call. Each step passes its own verb. Two copies drifted on the action before it was factored out.
- `Breached` is `len(Breaches) > 0 || exitCode != 0`, fail-closed on BOTH sides of the parse. A nonzero exit after a clean-looking report still blocks, because a command that emitted a partial report and then crashed is otherwise indistinguishable from a clean repository. The other half of the contract is short: a command that emits a valid report exits 0. A command that signals its own breach with a nonzero exit is not following it, and advisory calibration is a high threshold rather than a second mode. The fallback finding says in its own text that the output did not parse, since a weaker gate belongs in front of the operator and not only in the evidence file. Regression: `TestEvaluateMetricsOutput_NonzeroExitBlocksEvenWhenTheReportIsClean`.
- Policy lives in the step, not the command: the trusted threshold and exemptions are applied by code a contributor cannot reach, which is why the command reports per-function scores instead of a boolean.
- Only a verdict naming at least one breaching function is auto-fixable (`metricsMeasuredABreach`). A verdict breached solely by a nonzero exit, whether the output did not parse or the report parsed clean and named nothing, carries an `ask-user` finding and returns `AutoFixable` false: an agent cannot repair "the metrics command did not run", and `metricsFixPrompt` opens by asserting a breach nobody measured. Regressions: `TestMetricsStep_MissingBinaryParksForTheMaintainer`, `TestMetricsStep_ParsedReportWithANonzeroExitParksForTheMaintainer`, `TestMetricsStep_BreachParksAutoFixable`.
- A configured command with no coverage parks for the MAINTAINER rather than passing. Three paths reach it, the Test step's agent-evidence path (no unit command runs, so no profile is written), `--skip test`, and `skip_steps: [test]`. Against an empty directory the command yields an empty report that parses clean and passes, which is the vacuous green issue 9 closed for Test. An agent fix round cannot fix "the Test step produced no coverage", so the split matches the Test step's own artifact guard.
- `NO_MISTAKES_COVERAGE_ROOT` is a separate variable from `NO_MISTAKES_COVERAGE_DIR` on purpose. The root is this step's READ source, the run directory holding every unit's subdirectory; `COVERAGE_DIR` is the Test step's PER-UNIT write target, wiped immediately before each unit's command runs. One repository shell function reading one name must not get a different directory depending on which step called it, and a metrics command pointed at a wiped per-unit directory would certify an empty repository. The Metrics step never sets `NO_MISTAKES_COVERAGE_DIR`.

**Agent-Authored Commits Re-Enter Validation (`runValidationStep`)**

- Format, Review, Test, Metrics, Document, and Lint all exit through `runValidationStep` (`internal/pipeline/steps/common_fix.go`); each `Execute` is a three-line call and the real body is `execute`. The helper commits a dirty worktree at the step's exit, then attributes the commit by comparing `StepContext.AgentInvocations()` around the round: a commit made in a round that invoked an agent is agent-authored and sets `outcome.RestartFrom = pipeline.RestartBoundary`, a commit a deterministic tool produced sets nothing. `(*StepContext).runAgent` is the single counting point, incremented before the turn and whatever it returns, since a timed-out agent may already have edited files. An agent-authored commit still skips the restart when `restartExemptCommit` (`internal/pipeline/steps/restart_exemption.go`) finds every changed path matched by the trusted-only `sctx.Config.Restart.ExemptPaths` glob list, because the commit carries nothing a gate needs to see again; `AGENTS.md` and `CLAUDE.md` are excluded unconditionally, in any directory, since they steer the agents that run in every later step and no glob can spell "*.md except these". The changed-path read (`commitPathsSinceHead`) diffs `--no-renames` from the round's starting head to `HEAD`, because rename detection would collapse a source file moved into `docs/` into its new path alone and read a code deletion as docs-only. The exemption is a property of the commit, not of the step that made it, which is why it lives in this shared helper and applies to every validation step alike. Regressions: `internal/pipeline/steps/restart_exemption_test.go` (`TestRestartExemptCommit`), `internal/pipeline/steps/restart_test.go` (`TestRunValidationStep_CommitAttributionMatrix`, `TestRunValidationStep_ConfiguredExemptListReplacesTheDefault`, `TestRunValidationStep_EmptyExemptListRestartsOnEveryAgentCommit`, `TestRunValidationStep_RenameOutOfSourceStillRestarts`, `TestRunValidationStep_ExemptCommitDoesNotArmTheChurnGuard`).
- The step that certifies must not modify the tree it certifies. A round that returns `ReviewApprovedHeadSHA` and exits with a dirty worktree therefore commits nothing and touches no certification: it parks (`residueGateOutcome`) listing tracked modifications as warnings and untracked non-ignored files as info. It fires on the recorded head rather than on the executor's later decision to publish it, because that decision is not knowable in the step. Approving means discard, applied through `pipeline.ApprovalResidueDiscarder` at both `ActionApprove` sites; fixing means the step's own fix round commits the residue and re-reviews the new head. Residue items are all `no-op`, so `--yes` discards when the round contributed no actionable findings of its own; carrying any auto-fix or ask-user item makes the unattended answer fix, which commits the residue and re-reviews. The round's `AutoFixable` is cleared either way, so an auto-fix round never tidies up and re-certifies without a human seeing that the certifying step left a mess. Never restore the old certification-drop: the boundary step cannot restart into itself, so a dropped certification is never re-earned and push dies on a NULL column three steps later.
- Both gate helpers clear `outcome.AutoFixable`, because the executor's auto-fix branch runs before the approval park. On the churn gate a fix round would discard the `ask-user` warning with the round and the operator would never see it; on the residue gate the fix round reaches a defensible tree but reaches it silently, which is the outcome that gate exists to prevent.
- Discard removes exactly the paths the park recorded on `RunShared.ValidationResidue`, which the step writes from git at the moment it raises the gate and every round of that step clears at its start. The gate's findings describe the leftovers to a human and decide nothing: `Finding.ID` is free-form agent text `NormalizeFindings` keeps verbatim, so a round returning residue-shaped IDs could otherwise name any file for deletion. The same record gates the call, so `Executor.discardApprovalResidue` fires only for a round that actually parked for residue and approving any other gate the certifying step raises touches no files. The record is in-memory, so a daemon restart forgets it and approving the recovered gate discards nothing, leaving the leftovers for the next validation step's exit commit; forgetting can only fail towards touching no files. A run can sit parked for hours and a human or driving agent may edit the worktree meanwhile; never go back to `reset --hard` plus `clean -fd`, which destroys work no gate ruled on. The guarantee is exactly that scope: a file outside the recorded list survives, one on it does not. Log the paths, not counts.
- The residue path list is NUL-separated and rename-blind (`git diff --name-only -z --no-renames HEAD` read through `git.RunRaw`). `--no-renames` because rename detection collapses a staged rename into the new path alone, so discard restores that and leaves the staged deletion of the old one behind while every recorded path really is gone. The NUL separator because `core.quotePath` C-quotes any path with a non-ASCII, control, quote, or backslash byte, and that token reaches both the operator and git's pathspec parser. Discard restores through `git restore --source=HEAD --staged --worktree`, not `git checkout HEAD --`: the tracked list includes a staged-added path HEAD does not contain, and checkout aborts the whole invocation on that unmatched pathspec without restoring anything. Untracked paths go through `clean -ffd` (`git.UntrackedFiles` lists with `--untracked-files=all`, so an ordinary untracked directory arrives already expanded per file and the only entry that stays a directory is an embedded repository, which needs `-d` to be treated as one and the second `-f` to be removed rather than skipped), and the discard then re-reads the worktree and fails naming any recorded path that survived, so a silent no-op cannot report success. Every recorded path reaches both commands wrapped in `:(literal)` (`literalPathspecs`), because a residue path is a filename git handed back and not a pattern anyone wrote: unwrapped, a recorded `notes*.txt` makes `clean` delete an unrecorded `notes1.txt`, and a path starting with a colon reads as pathspec magic and never gets discarded.
- `pipeline.RestartBoundary` is `types.StepFormat`, which runs right after Rebase, ahead of Lint, Test, Metrics, Document, and Review. Format is the boundary and Review is the certifier, so the two roles the validation region needs sit on separate steps, and the CI step's two `RestartFrom` producers name the constant rather than a step literal. The park is keyed on the certifying step, not the boundary, so it needed no change for this split. Issue #8's reorder (Lint and Test ahead of Review, no push-time formatter backstop) is complete; see `docs/adr/0001-cheap-gates-before-review-and-restart-on-agent-commits.md` for the decision record.
- What makes a restart safe is `prepareRestart` (`internal/pipeline/executor.go`) revoking the run's review authority through `db.UpdateRunHeadSHAForRevalidation`, one statement for the head and the NULL approval so a crash between them cannot leave a certification covering an ancestor of the head. It owns the restart-time revocation and the soft-cap warning; no step revokes review authority as part of a restart. The one other writer is `CIStep.recordLocalRepair` (`internal/pipeline/steps/ci_fix.go`), which revokes while advancing the head to its own repair commit, something `prepareRestart` cannot do since it passes the run's existing head straight through. Every write is fail-closed, and `ErrInvalidRestartBoundary` separates a step naming a bad boundary from a failed write, so a database fault is not reported as a step bug. `Executor.honourRestart` is the single place a restart is acted on and `prepareRestart`'s only caller, so its handling covers every `RestartFrom` producer: a boundary this run was told to skip never rewinds, because rewinding to a skipped step re-marks it skipped and walks back to the requester, repeating agent passes while nothing revalidates. Whether that kills the run turns on publication. With Push live it fails with `ErrRestartBoundarySkipped` naming both steps, since push would otherwise refuse on the NULL certification three steps later naming nothing about the skip. With Push skipped too (`--skip review --skip push`, the documented validate-without-publishing mode) `declineRestart` drops the request with a log naming both steps and the run continues, because nothing reaches a remote and no certification is load-bearing. That drop happens in `executeStep` before the round acts on `RestartFrom`, so the round keeps the auto-fix branch and approval park it would have had if the step had never asked; deciding after the round had broken out let an ask-user finding ride into a completed run with no human seeing its gate. Both readings of the skip set come from the same place after a daemon restart: `startRun` writes the operator's list to `runs.skipped_steps` (a JSON array) and `Resume` reads it back through `adoptRecordedSkips` rather than resuming with an empty set. The step rows cannot answer this. A pending Push row means "skipped" and "not reached yet" indistinguishably, so inferring from them turns a decline into a hard failure on exactly the `--skip review --skip push` run the decline exists for. A restart also outranks the round's auto-fix and approval park, and a review round that asked for a restart certifies nothing.
- Termination is uncapped on purpose: `ResetStepsFrom` leaves `step_rounds` intact so per-step auto-fix budgets never refill across a restart, and the helper's no-progress guard (`RunShared.LastRestartTree`, compared via `git rev-parse HEAD^{tree}`) parks the run (`churnGateOutcome`, an `ask-user` finding naming the step and the repeated tree) when a step re-commits the tree its own last restart produced, offering ship-anyway, one more re-check, or abort. Do not let that path walk forward to push instead; push then fails on a NULL certification and names nothing about churn. That guard is per-process and remembers one tree per step, so it narrows the loop rather than bounding it; `runs.restart_count` plus the `db.RestartSoftCap` warning are what make a genuinely divergent loop visible. Do not add a cap.
- A re-entry after a restart is not a fix round (`Fixing` stays false), so every re-entered step reads `sctx.PreviousFindings` on its non-fix path too, and only on that path: Test's evidence prompt and fix prompt run in one `Execute`, so a fix round that carried them into both pasted the same findings twice. A validation step must never implement `pipeline.ApprovalGateReconciler`: that reconciles through a copied `StepContext`, whose agent-invocation counter diverges from the original and would misattribute the round's commit to a tool.
- A parked gate's diff (`internal/daemon/stepdiff.go`) falls back to the round's exit commit only for a step that commits its own work at its exit (`pipeline.CommitsOwnWorkAtExit`) and only on proof the round advanced the head, read from `step_rounds.starting_head_sha` (now written for every step, not just Review). A gate whose step committed nothing gets the empty diff; guessing `HEAD~1..HEAD` there showed the previous step's commit as this step's work. Head movement under any other parked step is not that step's authorship: Rebase parks after replaying the branch onto upstream, and CI can park in the round its own local repair commit advanced the head.

**Pipeline step tests (CI latency)**

- Fake `gh`/`glab`/`git` on PATH must be the tiny helper at `internal/pipeline/fakecli`, compiled once per test process without `-race` (`stepstest.Init` / `LinkFakeCLI`). Do not re-exec the race-instrumented test binary as those names: that was ~0.8-1.1s per spawn and pushed `internal/pipeline/steps` into the 10-minute package timeout.
- CI-monitor tests live in `internal/pipeline/steps/citest` so no child of `internal/pipeline/steps` sits near that cap. Both packages run under `go test ./...`; do not move them behind the `e2e` tag.
- A CI-monitor test that sets a seconds-scale `ci_timeout` must call `pinCIMonitorClock(step)`. The monitor measures its idle timeout with `step.now` and re-arms it by resolving the base-branch tip, so a live clock makes the test assert that several fake-CLI spawns plus a git read finish inside that bound; when a loaded runner misses it the step returns its timeout outcome in place of the outcome under test, which reads as a real defect rather than a flake. `stepstest.PinnedCIMonitorClock` owns the rationale and `stepstest.AssertShortCITimeoutTestsPinTheClock` enforces it in both packages (`TestEveryShortTimeoutTestPinsTheClock`). A test that genuinely asserts the timeout drives its own advancing `SetNow` instead.

**Telemetry Shape**

- Read-only surfaces (`axi` home/status/logs, `status`, `runs`) emit NO remote telemetry at all. Agent status polling made those commands the dominant Umami volume; do not reintroduce `trackCommand`/`trackAxiSurface`/`ReadSurfaceGate` on them. Mutation surfaces stay full-fidelity via `trackAxiSurface`/`trackCommand`.
- Detailed performance evidence is LOCAL-ONLY (`agent_invocations` rows plus `runs.parked_ms`); never store prompts, outputs, diffs, or raw command arguments there (shape-guard test `TestAgentInvocations_PrivacySafeShape`) and never send run IDs, paths, session identities, or per-invocation records to Umami - the only remote perf data is three bounded counts on the terminal `run finished` event. The local/remote split is documented in `docs/src/content/docs/reference/environment.md`; read locally with `no-mistakes stats`.
- Session-fidelity metric counts and timing boundaries have ONE authoritative home, `internal/agent/invocationmetrics.go` (tool-category classifier, `InvocationMetrics`, `FreshInputTokens`, `PerRoundTokens`, `ModelTimeMS`); the codex adapter fills them from its live `exec --json` event stream (`codex_metrics.go`) and raw input/output/cache-read tokens plus the additive fidelity fields are nullable so a not-reported datum - including a failed or cancelled invocation - is stored as NULL, never a fabricated zero. Codex's live stream exposes neither the model (resolved best-effort from the `~/.codex/sessions` rollout) nor internal model-request counts (it batches one exec into a single `turn.completed`, so round-trips are counted from completed items and subprocess wait is the reader-timed tool-item interval); codex usage is cumulative across a resumed session, so per-round deltas subtract the same session's prior cumulative (`Result.SessionUsageCumulative`).
